## 一、开工输入与冻结契约（不可违反）

Phase 1 已按「A1–A5 全部默认方案定版」收口（R 已于 11/09 14:28 回复确认），以下约束**即刻生效**，改动只能走 changelog：

| 编号 | 冻结内容 | 对 Phase 2 的直接影响 |
|---|---|---|
| A1① | DAG 部分节点挂审批时，run 级保持 `running` | 断点语义下沉到 step 粒度；其他就绪节点**继续调度** |
| A1② | 失败策略默认**快速失败**（run→failed） | 任一节点失败即整图终止；"跳过继续"若要做属 Phase 2 新增决策，走 changelog |
| A1 总则 | DAG 节点生命周期映射到 10 态，**不新增状态** | 节点入队→`queued`、执行中→`running`、命中审批→`awaiting_approval`、失败→`failed`、全图完成→`completed`（done_steps==total_steps 且无 pending） |
| A2 | `execute_run(run_id, from_seq)` 签名与续跑语义**不变** | DAG 调度器只替换内部串行循环；`status==done` 的步骤跳过不重算；对话/审批/REST/SSE 全链路依赖此入口 |
| A3 | 并发槽 `runs.slots_used / slots_total` 按现状冻结（不加 `slot_cost`） | 调度器每节点启动 `+=1`、结束 `-=1`，超槽排队；槽大小=并行节点数上限 |
| A4 | `tools(name,label,risk,whitelist,description,enabled)` 字段冻结 | 新增工具**只插数据不改代码**；审批判定入口 `policy.requires_approval(tool, args)` 不动 |
| A5 | SSE 事件总线走 Redis 频道 `ai-team-os.events`，多 worker 已支持 | 调度器只需状态落库后 `events.publish(...)`；如需新事件类型（`node.skipped`、`slot.exhausted`）走 changelog |

## 三、任务分解（WBS）

### T0 · 交接与环境（0.5 天，11/14–15 周末完成）
- 解压 Phase 1 源码 zip，按 README 三条命令本地跑通（PostgreSQL 16 + pgvector + Redis）
- 通读 `state_machine.py` / `models.py` / `migrations/init.sql` / `events.py` / 执行器 `execute_run`
- 确认 5 个回归测试全绿作为基线
- **验收**：本地闭环可复现（对话→执行→审批→续跑→交付物+sha256）

### T1 · DAG 数据模型扩展（0.5–1 天）
- `steps` 增加 DAG 元数据：`node_id`、`depends_on`（上游节点列表）、可选 `agent`（绑定智能体）、`skill`（引用技能）；保持 `(run_id, seq)` 有序语义兼容
- 不新增状态、不动 10 态状态机；依赖关系表达尽量少改表（若必须加字段，整理 changelog 清单，11/13 前可请唐建淇顺带，过点后自己走 changelog 流程）
- 规划器产出：从"线性步骤列表"升级为"可解析为 DAG 的步骤+依赖声明"（规划 prompt 与解析器改造）
- **验收**：一条含并行/汇聚结构的测试 DAG 能落库并被解析为图；串行任务（无依赖）行为与 Phase 1 完全一致

### T2 · asyncio DAG 调度器核心（2 天，本阶段最大头）
- 替换 `execute_run` 内部串行循环：就绪集计算（入度=0 或上游全 done）→ 并发启动（受 `slots_total` 约束）→ 节点结束 `slots_used -= 1` → 重新计算就绪集
- 多节点并行 = 多个 step 同时 `running`，run 仍单一状态（经状态机迁移）
- 失败处理：任一节点 `failed` → 默认快速失败（run→failed，经 `transit`）
- 超槽节点排队等待（不出异常、可观测）
- 拓扑校验：入环/自依赖在入队前拒绝，给出可读错误
- **验收**：3 节点并行 + 汇聚 DAG 全绿；槽=2 时 5 就绪节点只有 2 个同时 running；含环图被拒

### T3 · 审批断点 × DAG 语义（1 天）
- 节点命中 `policy.requires_approval` → step 置 `awaiting_approval`、落 `approvals`（幂等键规则不变），**run 保持 running，其他就绪节点继续调度**
- approve → 该节点经 `execute_run(run_id, from_seq)` 从节点断点续跑，已 done 节点不重算
- reject → run→rejected；revise → 节点转 `awaiting_input`，补充输入后该节点重新排队
- **验收**：中风险节点挂起时无依赖关系的兄弟节点照常跑完；批准后全图完成；同键重复审批 409

### T4 · 工具风险管控接管（0.5–1 天）
- 接管 `tools` 注册表运营：梳理 Phase 1 现有工具条目，补齐 Phase 2 需要的新工具（多智能体场景常用：文件读写、搜索、代码执行等按 risk 分级）——**只插数据不改代码**
- 白名单策略核对（中风险白名单内免审）
- audit payload 按 B2 约定统一带 `run_id` + `step`
- **验收**：新增工具零代码上线并被审批策略正确分级；`approval.requested` 等事件 payload 字段完整

### T5 · 技能系统 v1（1 天）
- 技能定义：`提示词模板 + 工具组合 + 参数预设` 的结构化描述（新表或 JSONB，schema 自定，Phase 2 自己定版）
- 技能注册/启停（沿用 tools 的"插数据不改代码"风格）
- DAG 节点引用技能：规划器可产出带 `skill` 的节点，执行时展开为模板+工具组合
- 给 FYR（P2 迭代做技能市场）留好消费接口：技能查询 API + schema 文档
- **验收**：同一技能在两个不同 DAG 节点复用成功；技能禁用后相关任务给出明确报错

### T6 · 前端最小适配与事件（0.5 天）
- 多 step 同时 `running` 的运行态展示（复用现有 SSE 信号重拉数据机制，前端零大改）
- 事件发布严格"落库后 publish"；如需 `node.skipped` / `slot.exhausted` 等新事件类型，走 changelog（本期可先不做）
- **验收**：DAG 运行时前端能看到并行节点的实时状态流转

### T7 · 测试与交付（1 天，11/19–20）
- 回归：Phase 1 的 5 个测试保持全绿（串行路径不回归）
- 新增 DAG 场景测试：并行执行 / 汇聚 / 快速失败 / 审批挂起+兄弟节点继续 / 断点续跑不重算 / 超槽排队 / 环检测 / 审批幂等
- 交付物：源码 zip（含 README 与迁移说明）+《Phase2-交付报告》+《Phase2-Phase4 对接确认单》（沿用 Phase 1 的异步确认单模式，给 mmmm/FYR 对接口径）
- **验收**：全部测试通过；确认单发到项目留言，云端任务转 done
